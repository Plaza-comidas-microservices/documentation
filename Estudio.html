01

Responsabilidad de cada capa

Arquitectura hexagonal (puertos y adaptadores). Regla de oro: domain/ nunca importa nada de Spring, JPA o Mongo — ni una sola anotación de framework.

domain/

modelPOJOs
Objetos puros del negocio (OrderModel, RestaurantModel). Sin @Entity, sin @Document, sin nada que dependa de cómo se guardan.
apipuerto de entrada
Interfaces que el dominio expone hacia afuera (IOrderServicePort). La aplicación las llama; nunca al revés.
spipuerto de salida
Interfaces que el dominio necesita del exterior (IOrderPersistencePort, ITraceabilityPort). El dominio las declara, pero no sabe quién las implementa.
usecaselógica real
Donde vive la regla de negocio de verdad (OrderUseCase, EfficiencyUseCase). Implementa api, consume spi.

application/

dtorequest/response
Contrato HTTP — un DTO por operación, nunca compartido entre endpoints aunque se parezcan.
mapperMapStruct
Traduce DTO ⇄ Model sin código repetitivo de copiar campo por campo.
handlerpegamento
Orquesta: DTO → Model → usecase → Model → DTO. Es la única capa que conoce tanto el mundo HTTP como el dominio.

infrastructure/

input/restcontrollers
Recibe HTTP, Swagger, extrae el usuario autenticado del JWT vía SecurityContextHolder.
out/jpa · out/mongopersistencia
Implementación concreta de un puerto spi contra MySQL o Mongo — entidad/documento + repositorio + mapper + adapter.
out/restcomsumerllamadas salientes
Implementación de un puerto spi que llama a otro microservicio vía RestTemplate.
securitypropio de cada repo
JwtValidator / JwtAuthenticationFilter / SecurityConfiguration — cada microservicio valida el JWT por su cuenta.
02

Decisiones de diseño clave

Las que un evaluador probablemente va a preguntar "¿por qué lo hicieron así?".

restaurantId embebido en el JWT

Se agrega en el login del empleado, en vez de que mall le pregunte a users en cada request.

Por qué: evita una llamada de red extra por petición; el dato no cambia durante la vida del token.

Sin tabla de "Roles"

Los roles son un string fijo (ADMIN/OWNER/EMPLOYEE/CLIENT), no una entidad administrable.

Por qué: no hay requerimiento de administrarlos en caliente — agregar la tabla sería complejidad sin necesidad real (YAGNI).

El PIN vive en mall, no en messaging

Se genera y persiste junto al pedido, y messaging solo recibe un texto ya armado para enviar.

Por qué: mall es dueño del ciclo de vida del pedido; HU15 necesita validar el PIN ahí mismo.

Bloqueante vs. no bloqueante

HU14 (SMS) y HU18 (tiempos) sí bloquean si fallan. HU17 (logging de trazabilidad) no bloquea.

Por qué: sin el SMS o los tiempos, la operación no tiene sentido; trazabilidad solo observa, nunca debe tumbar el flujo de negocio.

MongoDB para Trazabilidad

Los logs de cambio de estado son de solo-escritura (append), sin relaciones, sin esquema que migrar.

Por qué: encajan mejor como documentos que como filas relacionales — no hay JOIN que hacer nunca.

Doble adapter de SMS por perfil

TwilioSmsAdapter (real) y LogSmsAdapter (simulado), intercambiables con SPRING_PROFILES_ACTIVE=log.

Por qué: poder demostrar el flujo completo sin depender de saldo/restricciones de una cuenta trial de Twilio el día de la sustentación.

03

¿Qué es Mockito?

Librería de testing que crea "dobles" de las dependencias de una clase, para probarla aislada sin tocar MySQL, Mongo o Twilio de verdad.

@Mock
Crea el doble de una dependencia (ej. @Mock IOrderPersistencePort orderPersistencePort) — un objeto falso que se comporta como tú le digas.
@ExtendWith(MockitoExtension.class)
Activa Mockito dentro de un test de JUnit 5 — sin esto, las anotaciones @Mock no hacen nada.
when(...).thenReturn(...)
"Cuando le pidan esto, respondé esto" — define qué devuelve el mock ante una llamada puntual.
verify(mock, times(n))
Confirma que un método sí (o nunca) se llamó, y cuántas veces — clave para métodos void donde no hay valor de retorno que comprobar (ej. logStatusChange).
doThrow(...).when(mock)...
Hace que el mock lance una excepción en vez de responder normal — para probar los caminos tristes (ej. "Twilio no responde").
En una frase: Mockito te deja probar OrderUseCase.markOrderAsReady sin un mall real corriendo, sin base de datos, sin Twilio — solo con actores de utilería que responden exactamente lo que ese escenario necesita.
04

HU14 a fondo — la más difícil

No fue la más difícil por la lógica de negocio (es simple), sino por todo lo nuevo que trajo de una sola vez.

Microservicio nuevo desde cero

Primera vez armando messaging-microservice desde el arquetipo: renombrar el paquete, decidir qué boilerplate botar (JPA no aplicaba, no hay persistencia).

Primera integración externa real

Twilio trajo fricción que ninguna documentación anticipa: cuentas trial que restringen SMS de texto libre hacia números de Colombia.

Orquestación de 3 microservicios en una sola operación

mall le pide el teléfono a users, genera el PIN, le pide a messaging que envíe el SMS — y solo si todo eso sale bien, persiste el nuevo estado del pedido.

La primera decisión "todo o nada"

Se estableció el patrón de no dejar el pedido a medias si una llamada externa falla — el mismo criterio que luego se invirtió a propósito en HU17.

Plan B para el día de hoy

LogSmsAdapter nació de esta HU, pero terminó siendo la salida que permite demostrar todo el flujo sin depender de que Twilio tenga saldo justo hoy.

05

Paradigmas usados

Orientado a objetos — encapsulación (modelos con getters/setters controlados, nunca campos públicos) y polimorfismo (los puertos api/spi son interfaces con implementaciones intercambiables: JPA vs. Mongo vs. REST, Twilio vs. Log).

Funcional (parcial) — en EfficiencyUseCase y TraceabilityUseCase se usan Streams de Java (groupingBy, mapping, collect) para agrupar y agregar datos, en vez de loops imperativos con listas mutables.

Declarativo — SecurityConfiguration describe qué debe pasar con cada ruta/rol, no cómo verificarlo paso a paso.

06

Patrones de diseño

Hexagonal arquitectura

El patrón "paraguas" de los 4 repos — puertos y adaptadores.

Adapter infra

Cada XxxJpaAdapter/XxxMongoAdapter/XxxRestConsumerAdapter traduce entre el mundo externo y el modelo de dominio.

Strategy vía @Profile

TwilioSmsAdapter/LogSmsAdapter: dos formas de "mandar un SMS", elegidas en arranque sin tocar quien las usa.

Dependency Injection constructor

Todo se inyecta por constructor (Spring o a mano en BeanConfiguration) — nunca un new dentro del dominio.

DTO application

Un DTO de request/response por operación, nunca reutilizado entre endpoints.

Mapper MapStruct

Traduce entre capas sin código repetitivo de copiar campo por campo.

Repository Spring Data

IXxxRepository/IXxxMongoRepository extendiendo JpaRepository/MongoRepository.

07

Cómo se logró reutilización

  • Los puertos desacoplan el qué del cómo: OrderUseCase funcionaría igual si mañana se cambia MySQL por otra base — solo depende de una interfaz.
  • getOwnerById en users-microservice se reutilizó tal cual para resolver "dame el contacto de un cliente" en HU14 — trade-off consciente de nombre poco alineado a cambio de no duplicar lógica idéntica.
  • El patrón RestConsumerAdapter (RestTemplate + @Value + try/catch) se repite igual en los 3 microservicios que necesitan hablarle a otro — mismo molde, coherente en todo el proyecto.
  • El trío JwtValidator/JwtAuthenticationFilter/SecurityConfiguration se replicó a propósito por copia (no una librería compartida) en mall, users y traceability — cada microservicio debe poder desplegarse y evolucionar sin depender de una dependencia común.
08

Cómo se previenen excepciones no controladas

  • Una sola excepción de negocio (DomainException) por microservicio, capturada por un ControllerAdvisor que la traduce a un 400 con { "message": "..." } — el cliente nunca ve un stack trace crudo.
  • Toda validación ocurre al inicio del método del usecase, antes de cualquier efecto secundario — si algo no es válido, se corta ahí (fail fast), nunca a medias.
  • Las llamadas externas (RestTemplate) están en try/catch que traducen la excepción técnica (RestClientException, etc.) a un DomainException con mensaje en español — nunca se escapa una excepción de infraestructura al controller.
  • Comparaciones defensivas contra null:
// evita NullPointerException si securityPin llega nulo
if (securityPin == null || !securityPin.equals(order.getSecurityPin())) { ... }

// cortocircuito: evalúa null antes que .isEmpty()
if (list == null || list.isEmpty()) { ... }
09

Por qué un UseCase aparte para eficiencia

Responsabilidad única. OrderUseCase ya es dueño del ciclo de vida completo del pedido — 5 operaciones que mutan estado (crear, asignar, listo, entregar, cancelar). EfficiencyUseCase es puramente de lectura: no cambia nada, solo consulta y calcula.

Semántica de fallo distinta. Si trazabilidad falla al loguear (HU17), el pedido sigue su curso. Si trazabilidad falla al responder los tiempos para el reporte (HU18), no hay reporte que mostrar. Son dos contratos de confiabilidad distintos — mezclarlos en la misma clase sería confuso.

Más fácil de testear y de hacer crecer. Aislado, se prueba con mocks más simples (sin arrastrar toda la maquinaria de PIN/SMS), y si mañana se agrega otro reporte, ese crecimiento no ensucia la clase que de verdad importa para que un pedido funcione.
